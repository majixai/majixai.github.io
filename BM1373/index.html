Spec ops overview

Power spec ops

Validate rail sequencing, current capacity, and brownout behavior before any timing work begins.

Clock spec ops

Keep oscillator assumptions explicit and keep burst timing within a logged, inspectable window.

Thermal spec ops

Track thermal rise, fan control, and cutback thresholds as first-class operational data.

Audit spec ops

Bind each board state transition to route and hash provenance so documentation stays trustworthy.

Signal and control blocks

  • Power block: input rails, regulation, surge handling, and safe enable sequencing.
  • Control block: host commands, board enable, reset, and status feedback.
  • Telemetry block: temperature, job health, share counts, and fault counters.
  • Timing block: deterministic work windows with bounded retries and recovery.
  • Audit block: route/hash checks for provenance, page lineage, and control integrity.

Bring-up sequence

  • Confirm rails are present and within their expected tolerance band.
  • Assert reset, then release the control plane once the board is stable.
  • Load the operational profile from the ESP32-side configuration.
  • Run a short timing burst and watch telemetry for anomalies.
  • Escalate to recovery mode if thermal or transport checks fail.

Spec ops matrix

Operational rules

  • Never let a burst outrun the ability to verify it.
  • Keep fallback paths visible and easy to reach.
  • Prefer observable counters over opaque acceleration.
  • Use the same terminology on the ESP32 page for shared transport semantics.
  • Keep the BM1373 page linked from the circuit hub and the miner stack.
