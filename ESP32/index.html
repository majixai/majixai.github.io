Spec ops overview

Boot spec ops

Define flash, reset, and startup checks so the board always lands in a known-safe state.

Network spec ops

Describe Wi-Fi, job polling, and reconnect behavior with short, deterministic state transitions.

GPIO spec ops

Track status LEDs, buttons, UART, and debug outputs as first-class operational controls.

Audit spec ops

Bind control frames and route changes to hashable metadata so navigation and telemetry stay aligned.

Control blocks

  • Boot block: flash validation, reset, and safe startup behavior.
  • Transport block: Wi-Fi connectivity, pool jobs, and retry/backoff logic.
  • IO block: LEDs, buttons, UART console, and status indicators.
  • Telemetry block: temperature, reconnect counters, and job health.
  • Governance block: router/hash validation for pages, payloads, and updates.

Bring-up sequence

  • Verify flash contents and reset behavior.
  • Bring up Wi-Fi and confirm the control plane has network reachability.
  • Load the pool or demo configuration and confirm worker identity.
  • Run a short status loop to confirm telemetry and LED behavior.
  • Escalate to recovery mode when transport or thermal checks fail.

Operational rules

  • Keep network loops short and recoverable.
  • Prefer inspectable counters over silent state changes.
  • Keep fallback access through serial or browser controls.
  • Mirror terminology with the BM1373 page for shared transport semantics.
  • Keep the ESP32 page linked from the circuit hub and miner stack.
